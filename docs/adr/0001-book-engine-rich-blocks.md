# ADR-0001：站点即 book engine——富文本块的渐进增强

- 状态：已接受
- 日期：2026-08-11
- 决策者：antinomie（与 Claude 结对）

## 背景

这本书的内容同时活在两个地方：

1. **GitHub 仓库**（`agent/*.md`）——书自己在 00 章里写明"这本书自己也躺在仓库里"，读者会在 GitHub 上直接阅读源码；
2. **Vue 站点**（`web/`）——通过 Vite `?raw` 把同一份 md 打进 bundle，浏览器端 markdown-it 渲染。

随着写作推进，纯 markdown 的表达力开始不够：01 章的两张架构图（依赖方向图、文件全貌图）只能以 ASCII 画在代码块里。ASCII 图在 GitHub 上是合理呈现，但在站点上它和整站的设计语言（几何、圆、三色字体分工）格格不入，也无法承载交互。

可以预见这不是孤例：之后还会有更多"在网页上值得做得更丰富"的内容块（更多图、可展开的注释、也许可运行的示例）。因此需要一条**通用规则**，而不是每张图一个临时方案。

## 决策

**把 Vue 站点定义为一个 book engine 的实例：markdown 是唯一内容源，engine 只增强、不改写。** 具体四条：

1. **单一事实源**：所有正文（含图的内容）只写在 `agent/*.md` 里，站点不私藏内容。任何富文本块在 md 中都必须保留一份**完整的纯文本版本**（如 ASCII 图）。

2. **标记方式：自定义 fence tag**。需要增强的块用带命名空间的代码围栏语言标记，如 ```` ```diagram-filemap ````。engine 遇到认识的 tag 就把该块替换为真正的组件；不认识的 tag（包括 GitHub、编辑器预览、任何其他 markdown 阅读器）按普通代码块原样渲染——纯文本版本自动兜底。

3. **组件标签是 engine chrome，按 locale 供给**。图内的标注文字（模块名、说明）不属于正文，不写在 md 里；它们作为引擎的界面文案放进 `web/src/i18n/messages.js`，随界面语言切换。md 里的纯文本版本仍随各语言目录（`agent/en/`、`agent/es/`）各有一份。

4. **增强必须是渐进的、可降级的**。组件挂了、JS 没跑、读者在 GitHub 上——任何情况下内容都完整可读。增强只许做纯文本做不到的事：排版贴合站点语言、hover 高亮、点击跳章。

## 备选方案

- **图片（SVG 文件 + `![]()`）**：GitHub 也能看，但不可交互、文字不可选、三语要维护三份图片、无法响应站点字体与配色。否决。
- **纯 web 组件，md 里删掉 ASCII**：GitHub 阅读体验崩塌，违背"书也躺在仓库里"的承诺。否决。
- **不做，保留 ASCII**：零成本，但图与站点设计语言冲突是持续的视觉债，且放弃"图即导航"的交互收益。否决。

## 后果

- **正向**：GitHub 与站点各得其所；未来所有富文本需求有章可循（新 tag + 新组件，不动内容管线）；`diagram-*` 构成预留命名空间。
- **代价**：同一信息两处维护（md 的 ASCII 版 + 组件的数据结构），图内容变更时要两边同步——架构图更新频率低，可接受；组件标签要配齐 zh/en/es 三套。
- **约束**：engine 组件必须遵守 `web/DESIGN.md` 的设计词汇（三色字体分工、墨色线条、蓝色只给"循环"本身），不得引入新的视觉语言。所有 `diagram-*` 组件与其图形原语（箭头、框、连线）集中在 `web/src/components/diagrams/` 这个 engine 组件库内复用，不散落到站点全局样式。

## 首个实例

`diagram-filemap`（01 章文件全貌图）：engine 渲染为分层图组件，hover 模块高亮并提示所在章节，点击跳章。md 中保留 ASCII 原版。
